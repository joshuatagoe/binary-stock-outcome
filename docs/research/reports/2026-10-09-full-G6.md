### D4 (decision)

Leading answer: follow the spec's preferred stack. (1) Contract: Rust with Anchor (current line is 1.2.x, released 2026-10-06, hosted at solana-foundation/anchor) on Solana. (2) Frontend: Next.js with React and TypeScript, using @solana/kit (the renamed web3.js 2.x line) plus the Solana wallet adapter, with a Codama or IDL-generated client. (3) Automation service: TypeScript on Node.js in the same repo, exposed both as a long-running scheduler and as one-shot CLI commands (morning job, settle job) so a grader can trigger each step by hand. Costs of the alternatives. Solidity on an EVM L2: the spec itself warns of order-book latency, and it adds a second toolchain. Pinocchio (no_std, lower compute units): more manual account validation and instruction routing, which is only worth it if you write your own order book and hit compute limits. Native Rust without a framework: more boilerplate and more room for account-validation bugs. Python or Rust for automation: leaves the spec's stated TypeScript preference and splits the repo's languages. HyperLiquid: do not build on it, but document the feasibility. The spec only requires that you 'research and document feasibility if you explore this path'. S24 also needs alternatives considered, so write a short note. HIP-4 outcome markets are live (BTC daily binary, validator-curated templates, settled in USDH, deployer-submitted settlement), HIP-3 needs a 500k HYPE stake, and neither lets you deploy your own program with your own mint/vault/settle/redeem invariants or a MAG7 close feed. The HyperEVM-to-order-book write path is documented inconsistently.

**Against:** Anchor 1.x is new and brings churn: the TS package moved to @anchor-lang/core, duplicate mutable accounts now error, Solana 3.x is required, and 'anchor test' now runs Surfpool, whose Windows support is undocumented. Anchor adds compute-unit overhead, which matters if you build a minimal on-chain order book. Phoenix and Manifest are not Anchor programs, so integrating them by CPI means hand-written instruction builders anyway. @solana/kit has no first-class Anchor support (its own README says Anchor support in create-solana-program is 'coming soon'), so many tutorials and the wallet adapter still assume legacy web3.js types and you may need @solana/compat. A grader could also read HyperLiquid as the closest existing 'binary outcome' venue: HIP-4 was live on mainnet by May 2026 and the Polymarket-style product is exactly what the spec describes, so a thin feasibility note could look dismissive. The note must say why a custom MAG7 close-above-strike product does not fit (validator-approved templates, hlPerp-keyword underlyings, no own program).

### D11 (decision)

Leading answer: yes, add a clearly separated simulation (demo) mode, but keep real-oracle settlement as the primary path and make the two visibly different. Reasons. (a) Real equity oracle prices only move on US trading sessions and weekdays (Pyth lists 9:30-16:00 regular, pre/post sessions, an overnight session Sun-Thu, closed weekends and NYSE holidays), and on devnet you cannot warp the clock, so a grader running at night or on a weekend cannot see settle at 'after 4:00 PM ET' without something simulated. (b) Comparable venues keep a separate sandbox with fake money and separate credentials (Kalshi demo environment says prices and behaviour may not reflect real markets; Stripe test clocks simulate time passing for billing). (c) In automated tests you already need a fake clock and fake oracle accounts: LiteSVM can set the Clock sysvar, warp slots and write arbitrary accounts, so the test suite proves the logic regardless of the hour. Shape of the demo mode: a separate config or deployment (own program-owned mock price account with the same layout and the same staleness and confidence checks, short expiry markets such as 'settle in N minutes'), never reachable from the production config, labelled in the UI and README, and the 'real' path still demonstrated with a recorded or live market-hours run. Same settle code path, different price account and time source.

**Against:** A mock oracle can look like bypassing the spec's core requirement that settle 'must read the stock's closing price on-chain from the oracle'. If the demo flag lives in the settlement path it is an attack surface and a grading risk, and a grader may judge the headline lifecycle as faked. 'Real oracle only' is simpler, cheaper to build and test, and avoids two code paths; it can still be reproducible if the grader runs during market hours or if the program can settle a past timestamp from a historical oracle update (not verified; see Q24). Real devnet already carries real Pyth data (the receiver is deployed on devnet and the README example posts mainnet Hermes data to devnet), so a market-hours run is a true end-to-end. The spec says nothing about a simulation mode, and graders may value the faithful run more than convenience. Also, Pyth now needs a Hermes API key (free trial, then paid), so the real path is the fragile one for graders, which argues for a keyless demo mode rather than against it.

### D18 (decision)

Leading answer: Solana (devnet for the required deployment), with the market functions (create strike market, mint pair, settle, admin settle, redeem, pause) and the vault invariant in the project's own Anchor program, as the spec recommends. For the order book, either a minimal CLOB inside the program (strongest on 'in your own program') or a CPI to an existing CLOB (Phoenix legacy is MIT-licensed; Manifest is GPL-3.0, interacts via a wrapper program, and publishes a Certora formal-verification claim), with the vault/mint/redeem logic still in the project's program. The documentation must be honest about 'sub-second finality': Solana's 'confirmed' commitment is a supermajority vote, not rooted finality; the legacy TowerBFT figure of about 12.8 s to finality is secondary-sourced; Anza's Alpenglow targets about 150 ms and went live on testnet (9/24) and devnet (9/25) but mainnet-beta is only 'upcoming'. Other candidate chains and what the docs must say. EVM L2s (Base Flashblocks about 200 ms pre-confirmations from the sequencer; Arbitrum L2-to-L1 finality is about 6.4 days; MegaETH advertises about 10 ms blocks): the 'finality' is a sequencer promise, so the doc must explain how order-book latency is handled. HyperLiquid: sub-second latency (median 0.2 s, p99 0.9 s) but outcome markets are template-based and deployer-settled, so the product's own invariants cannot live in a user program. Sui: Mysticeti commits in about 0.5 s in benchmarks, DeepBook is a native CLOB callable from Move, and DeepBook Predict (mainnet and testnet from 2026-09-12) is a close analogue but at the last read its markets had expired unsettled and quotes and mints aborted. Injective has a native exchange module with an on-chain order book but this is chain-native code rather than your own program. Aptos, Sei, Monad were not verified (search budget ran out).

**Against:** Read literally, Solana does not have sub-second finality today; only optimistic confirmation. Alpenglow's finality is a target, mainnet has no date, and the project would be graded against a devnet that switched consensus on 9/25, so devnet behaviour is less known than before. Sui could meet 'sub-second' and 'native CLOB' more literally, has a documented Move integration path and an official prediction-market module, and avoids Solana's devnet reset risk, but the grader's spec names Solana as recommended and Solana devnet as required to pass if Solana is chosen, and the Sui prediction module showed a stalled state. The 'own program' requirement is also ambiguous for the CLOB: using Phoenix or Manifest places matching outside the project's program, and Manifest requires a wrapper CPI, so the strictest reading favours building a minimal book, which is the highest-risk path.

### D30 (decision)

Leading answer: a layered plan that covers the spec's four bullets and the gaps. Tools current as of 2026-10-09: Anchor 1.2.1 (latest 2026-10-06) whose 'anchor init' now generates a LiteSVM Rust test template by default; Mollusk (single-instruction harness with compute-unit benchmarking); Surfpool (now what 'anchor test' runs instead of solana-test-validator); 'anchor fuzz' (Crucible, coverage-guided with invariant functions run after each action); Trident 0.11.1 as an alternative fuzzer; solana-bankrun is deprecated in favour of LiteSVM. Plan. (1) Unit tests per instruction in LiteSVM, plus Mollusk for CU budgets. (2) Settlement table tests: at-strike, above, below, plus boundaries and exponent/scale conversion. (3) Invariant tests: vault balance = $1 x pairs minted after every mint and redeem; Yes payout + No payout = $1 over a price grid and by property/fuzz (the u64 price domain cannot be enumerated). (4) Lifecycle tests in LiteSVM with Clock set to ET times: all four trade paths and a multi-user scenario. (5) A devnet smoke script run for real. Areas the spec's list leaves out: order-book correctness (price-time priority, partial fills, tick/lot rounding, self-trade, cancel, escrow counted in the vault invariant); oracle account validation (wrong feed id, wrong owner, verification level, negative price, publish time in the future, exactly-at-threshold staleness/confidence); calendar and time (weekends, NYSE holidays, early closes at 1 p.m. ET on 2026-11-27 and 2026-12-24, DST on the ET clock); automation service (idempotent create when PDA exists, retry/backoff, crash and restart mid-job, partial failure across 7 stocks x strikes, missed-run catch-up, RPC 429s); access control and pause; account substitution and duplicate-account attacks (Anchor 1.0 now errors on duplicate mutable accounts unless 'dup'); double redeem and late redeem; transaction size/compute for the atomic Buy No path; strike generation and dedup.

**Against:** Breadth risk: this is a lot for a project that must also ship a frontend and a devnet deployment, and the spec's list may be enough to pass. The fuzzers are young (Crucible has no published releases and 63 stars; Trident is 0.11.x), so a hand-written boundary table may be more reliable. LiteSVM injects accounts directly, so it never exercises the real Pyth receiver verification path or real Wormhole data; only a devnet run does, and that needs a Hermes key. Rust LiteSVM tests plus TypeScript frontend/automation tests means two test ecosystems, and Anchor 1.0 moves the default to Rust while the spec's frontend and automation are TypeScript. If the project uses an existing CLOB by CPI, the order-book tests shrink and the integration risk grows, so the plan changes with the D18 choice.

### A2 (decision)

Leading answer: treat devnet as an unreliable, unpublished-uptime environment and keep your own tamper-evident record. Facts. Solana's docs say only that devnet 'may be subject to ledger resets', the public endpoint is a single rate-limited node, and status.solana.com lists no devnet component, so there is no official devnet reliability record to cite. I found no published devnet halt history (all halt histories found are mainnet-beta: 2022, 2023, Feb 2024, and an Aug 2026 near-miss). Devnet has also just taken the Alpenglow consensus change (9/25). What to do. (1) A run log written by both jobs and a heartbeat: UTC and ET time, RPC URL, getSlot, getHealth, getGenesisHash, the LastRestartSlot sysvar (implemented since Agave 1.17), tx signatures, job outcome. A changed genesis hash or restart slot shows a reset or restart. (2) Hash-chain the log entries and commit daily; optionally stamp with OpenTimestamps (free, no API key, Bitcoin-anchored, proves the file existed before a time, offline verification), which avoids touching mainnet, which the spec forbids for the core submission. (3) Mirror the same scripts on a local validator or Surfpool so the day is reproducible. (4) Keep deploy scripts idempotent with the same program keypair so a reset only needs a redeploy and re-init. Note getBlockTime is an estimate from validator vote timestamps, so use your own clock plus slot for the record, not block time alone.

**Against:** The record is self-attested: it cannot prove an outage was devnet's rather than your RPC provider's (the public devnet node is shared and rate-limited, 429/403 possible). OpenTimestamps proves only that data existed before a time, not that it was true. It adds moving parts that the spec does not ask for, and graders may care only that the reproducible scripts run. The actual record of devnet outages may be small (I found none), so the problem may be hypothetical, and the simplest honest answer is a one-line limitation: 'devnet may reset; use the local-validator path'. Devnet's switch to Alpenglow on 9/25 could change reliability in either direction and I could not find data.

### Q23 (open question)

Options and their evidence, no pick. Spec text: 'Markets created before market open and settled within 10 minutes of market close every trading day'; success criteria repeat 'within 10 minutes of market close'; and settlement is only possible if the cluster is up. The spec has an admin-override path with a time delay (e.g. 1 hour), and says unredeemed tokens remain redeemable indefinitely, so a late settle after recovery is allowed by design but breaks the 10-minute metric. (A) Count the day as a miss and report the raw rate. Evidence: spec has no exception clause for chain outages; simplest and most honest; hurts the metric with a cause you do not control. (B) Report two numbers: raw, and adjusted that excludes days where the heartbeat log shows devnet not advancing slots or a changed genesis hash / LastRestartSlot, with evidence attached (see A2). Evidence: Solana's docs themselves warn devnet may reset; there is no official devnet status feed, so the proof has to be yours. Risk: graders may reject self-declared exclusions. (C) Run a shadow settlement on a local validator or Surfpool for the lost day to show the service would have met the target. Evidence: shows service correctness, but not devnet liveness. (D) Define 'trading day' precisely using the NYSE calendar (holidays; early closes at 1:00 p.m. ET on 2026-11-27 and 2026-12-24) so that non-days are not counted as misses; note the spec fixes 4:00 PM ET and does not discuss early closes. (E) Ask the graders: state the proposed definition in the README before any outage and ask through the submission channel for a ruling; pre-registering the definition avoids looking like after-the-fact excuse-making. I did not find any evidence of how the Gauntlet graders treat this; that is a question for them.

**Against:** What would change the picture: a grader statement or rubric text saying the metric is measured on mainnet-like conditions or counts only days the cluster was up; evidence from heartbeat logs that most lost days are the project's own RPC or hosting failures rather than devnet halts (which would make exclusions indefensible); documented devnet outage frequency after Alpenglow (none found); or the project deploying the automation to a hosting option with its own downtime (e.g. GitHub Actions schedules can be delayed, dropped, or disabled after 60 days of repo inactivity), which would make the miss the project's fault rather than devnet's.

### Q24 (open question)

Options and evidence, no pick. Facts first. Pyth's market-hours page lists US equities regular session 9:30-16:00 ET weekdays, pre-market 4:00-9:30, post-market 16:00-20:00, overnight Sun-Thu 20:00-04:00 (Blue Ocean ATS), closed weekends and NYSE holidays; Pyth's best-practice page says outside hours 'it's not clear what an equity's price is'. ### Q55 (open question)

Options and evidence, no pick. What the one command needs. (a) A Solana toolchain: Solana's installer covers Mac, Linux and WSL and installs Rust, Solana CLI, Anchor CLI, Surfpool CLI, Node and Yarn; the docs say Windows users 'must use Windows Subsystem for Linux (WSL)', while Anza's own CLI install page gives a native Windows installer; the two sources contradict, so native Windows support stays unconfirmed (and an open Agave issue reports solana-test-validator not working properly on Windows, secondary). (b) A local chain: Anchor 1.x 'anchor test' now runs Surfpool, whose install options are a bash curl script, cargo build or a Docker image; Windows is not mentioned. (c) An oracle key: Hermes now requires a Pyth API key (Bearer header) from Pyth Terminal, free trial then paid plans; the key is the likeliest thing to block a grader on day 2. (d) Devnet SOL: the Solana faucet allows 2 requests per 8 hours, asks AI agents not to use it, and lists CLI airdrop, a proof-of-work faucet and a local validator as alternatives; the public devnet endpoint is rate-limited. Options. (1) Docker/devcontainer: one image holding Rust, Solana, Anchor, Node; 'make dev' (or a node/just script) runs inside; works on all three OSes with Docker installed but needs Docker Desktop on Windows/macOS; unverified how Surfpool in Docker behaves. (2) Native scripts plus WSL documentation: Windows grader runs 'wsl --install' (admin and possibly restart) then make dev inside Ubuntu. (3) Two tiers: 'make dev' is fully local (local chain, mock or recorded oracle, no keys, no faucet) and 'make devnet' needs keys and funded SOL; reduces blockers to near zero for the first command. (4) A TypeScript task runner (npm scripts) instead of make, since GNU make is not installed on Windows by default (UNCONFIRMED). What would block it: WSL/Docker not installable, no admin rights, long first-time Rust/Solana downloads (unmeasured), expired or missing Pyth key, faucet limit hit, public RPC 429, devnet reset or outage.

**Against:** What would change the picture: a test run on clean Windows 11, macOS and Ubuntu machines with timings; confirmation that Surfpool and 'anchor test' work natively on Windows (not documented); whether Pyth issues a key that survives for the grading window and whether the grader will create one; whether graders accept a WSL or Docker prerequisite as 'one command'; and whether the Gauntlet environment gives graders devnet SOL or a keypair.
