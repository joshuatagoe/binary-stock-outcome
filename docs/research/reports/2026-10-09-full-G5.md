### D17 (decision)

Follow the spec (environment variables plus a committed .env.example), but split by role and by environment. (1) .env.example lists variable NAMES only, with placeholder values and a comment for each saying who holds it and what it can do. The real .env is gitignored and covered by a secret scanner (GitHub secret scanning or a pre-commit tool). (2) Three separate secrets with separate keys: the admin key (config, pause, override), the automation wallet (daily create and settle), and the oracle API key (Pyth Hermes). The admin key must NOT live in the backend's .env at all. Use a hardware wallet or a Squads multisig for it; the backend should only be able to do daily jobs. (3) For keypairs, put a file PATH in the env var (for example AUTOMATION_KEYPAIR_PATH pointing outside the repo) rather than the raw secret bytes. That keeps the secret out of process listings, crash dumps and logs, and OWASP prefers mounted secret files over raw env vars. (4) Devnet keys are throwaway and funded from the faucet. For the mainnet bonus the automation wallet holds only a small float and its key comes from a secrets manager or KMS. (5) The Hermes API key is now mandatory (since 26 Aug 2026, sent as a Bearer token), so it is a real secret and must never reach the browser bundle. (6) Redact keys, bearer tokens and RPC URLs that carry keys from all logs. Document a rotation runbook: rotate first, scrub history second.

**Against:** Raw environment variables are the weakest of the common options. OWASP says env vars are generally accessible to all processes and may land in logs or system dumps, and to use them only when other injection methods are not possible. Anza says file-system keypairs are the least secure wallet type. A .env file is exactly the config-file-in-the-repo-directory mistake that 12-factor warns about. For mainnet a KMS or HSM-backed Ed25519 signer is the stronger answer. On the other side, the spec says 'Secrets via environment variables; provide .env.example' in plain words, so departing from it costs grading clarity. For a devnet-only core submission, a KMS is over-engineering. A defensible middle path is env-var interface now, with a documented upgrade path to KMS for the mainnet bonus (S22).

### D19 (decision)

Design for 'the chain is the only clock that matters and the backend is a stateless catch-up loop'. PROGRAM: (a) trading cutoff by on-chain clock. Mint, order placement and fills are rejected once Clock >= the market's close timestamp (4:00 PM ET), so that when the chain returns nobody can trade or mint against stale resting orders with the closing price already public. Cancels and redeems stay allowed. This is the same idea as Chainlink's sequencer-uptime guidance (do not let the first post-outage transactions exploit stale state). (b) Settlement must not depend on 'price no older than 5 minutes from now', because after a halt every price is old. Check instead that the oracle update's publish_time falls inside a short window just after the close, and that confidence is within the threshold. Pyth documents fetching the price for a specific timestamp from Hermes for delayed settlement. (c) Keep the spec's admin override (after the 1-hour delay measured from close) as the fallback when no valid in-window price exists. Do not void markets: with single tokens in the wild a void cannot be made fair. BACKEND: a slot-progress watchdog (getHealth / slot not advancing) that alerts; every action is idempotent (read the market account first, skip if already settled or created); fresh blockhash on every attempt (blockhashes live only about 60 to 90 seconds); no blind replay of queued transactions. The 15-minute retry window starts when the chain is healthy again, not at 4:05 PM. Morning job: if the chain is down at 8:00 AM, retry; do not create markets after a cutoff time on the day (document the cutoff). WEBSITE: a banner driven by chain health (slot lag), order and mint buttons disabled, countdown based on chain time, last-known prices labelled stale; after recovery show 'closed, settling' for expired markets, then the outcome. DEVNET NOTE: devnet may be ledger-reset, which wipes all program state, so deploy and lifecycle scripts must be re-runnable from zero.

**Against:** (1) Over-engineering: no documented devnet halt turned up, and mainnet has had no full halt since Feb 2024 per Helius. The simplest policy is 'after any outage, use admin override'. The spec already provides it and the 1-hour delay makes it safe. (2) The window-based price check weakens the spec's literal requirement (reject prices older than e.g. 5 minutes) and adds attack surface: a caller could choose among several valid in-window updates, so a canonical rule (for example the first update at or after 16:00:00) is mandatory. Pyth equity feeds also run after-hours sessions (post-market 4 to 8 PM), so a loose window could pick a post-close print. (3) Pyth now needs a Hermes API key and the timestamped endpoint path was not confirmed in this review. (4) Cutting trading at the on-chain cutoff means users locked out by an outage cannot exit positions even if they would have wanted to before 4 PM; that is a fairness cost, not just a safety gain. (5) Early-close days (1 PM ET) are not handled by a fixed 4 PM cutoff.

### D22 (decision)

Anchor 1.x, pinned to one version (1.2.1 is current as of 6 Oct 2026; 1.0.0 shipped 2 Apr 2026), installed with AVM and built inside WSL2 Ubuntu (the Solana and Anchor install docs say Windows needs WSL). Tests: the LiteSVM template (the default from Anchor 1.0) for fast in-process unit and invariant tests, optionally Mollusk for single-instruction compute-unit checks, and Surfpool (default runner for anchor test) or devnet for the full lifecycle script. Client: generate the TypeScript client from the Anchor IDL with Codama (@codama/renderers-js, Kit-compatible, maintained by Anza) and use @solana/kit in the frontend and backend, because @anchor-lang/core only works with legacy web3.js v1. If the team prefers one fewer dependency, the Anchor client is acceptable but ties the whole stack to web3.js v1. Not native Rust (all account validation by hand, more audit burden) and not Pinocchio (zero-dependency and lower compute, but manual checks, and its README gives no production-readiness statement). The spec prefers Anchor and asks to justify major dependencies, so the justification is: constraint macros (has_one, seeds, close, mint::authority) remove whole classes of account-validation bugs in a contract whose main risk is money invariants, not compute cost.

**Against:** (1) Anchor 1.x is under 7 months old, has had three minor lines (1.0, 1.1, 1.2) and a Solana v4 crate feature added in 1.2.1, so tooling churn is real; the docs' canonical repo is otter-sec/anchor, so check maintainership continuity. (2) Two client stacks in the same repo (Anchor IDL plus Codama plus Kit) adds a generator step; the spec says avoid unnecessary abstractions. (3) Pinocchio's gain only matters if the program is compute-bound, for example if we write our own order book inside the program; if a CLOB such as Phoenix or OpenBook is called via CPI, compute is dominated by the CLOB. (4) Windows: WSL2 is documented, but this repo lives in a OneDrive-synced folder; building Rust inside a synced folder or across /mnt/c is slow and error-prone (UNCONFIRMED inference), so the repo may need to live in the WSL filesystem. (5) The Anchor CLI examples show Node/Yarn only for TS templates, so a pure LiteSVM Rust test flow could drop Node from the program build, but the backend and frontend still need it.

### D23 (decision)

Three parts with a hard trust boundary. ON-CHAIN (Anchor program plus an external or embedded CLOB): custody of all USDC in per-market vault PDAs; the only place that can mint or burn Yes/No tokens; stores strikes, close times, settlement outcome; enforces the $1.00 invariant, time rules, roles and pause. It must never depend on the backend for correctness. BROWSER (static React app): reads chain state and prices, builds transactions, every state change needs the user's wallet signature. It must never hold a secret or a signing key, never custody funds, and never be trusted for position-constraint enforcement (the spec's 'can't hold both' rule is UI-only unless the program enforces it). ALWAYS-ON SERVICE (Node/TypeScript, same repo): a keeper with the automation wallet that runs the morning job (create markets) and the settlement job (settle, retry, alert). It can only call the few instructions the operator role is granted. It must never be able to move vault funds, mint tokens, redeem for others, change a written outcome, upgrade the program or hold the admin key. Liveness depends on it, safety does not: if it dies, markets still hold funds and the admin override and permissionless settlement still work. Comparable designs: OpenBook v2 splits market roles (open-orders admin, consume-events admin, close-market admin, collect-fee admin) and Phoenix is crankless so no keeper is needed to keep the book running; Pyth price posting is permissionless, so anyone can supply the oracle data.

**Against:** (1) A keeper plus a static site is more moving parts than needed: a GitHub Actions cron could replace the always-on service, but GitHub documents that scheduled runs can be delayed under load, run at best every 5 minutes, and are disabled after 60 days without repo activity in public repos, which breaks the 30-second retry loop and the 4:05 PM promise. (2) Pyth's Hermes now needs an API key, so either the browser gets prices through the backend (the static site then depends on the service for prices) or the key is exposed. (3) The spec says the order book is the 'trading venue' but also allows building one in the program; the choice changes what the program may do (an embedded book makes the program a matching engine, with much larger audit scope). (4) Splitting 'operator' from 'admin' adds an extra role to test; some teams would accept one key for the demo.

### D24 (decision)

Roles: ADMIN (cold key, multisig on mainnet) and OPERATOR (the automation wallet), plus anyone. initialize_config: once, signer must be a designated deployer (ideally checked against the program's upgrade authority) so nobody can front-run it. Config changes (tickers, oracle feeds, thresholds, rotate admin): admin only, two-step handover. create_strike_market / add_strike: operator or admin, only before the trading cutoff. mint_pair: anyone, when not paused and before close. place / cancel orders: any user for their own orders; cancel always allowed; a market authority may force-cancel only in a closed state (Phoenix does this). settle_market: ideally anyone can call (the outcome is a pure function of a validated oracle update); the backend is only the usual caller. admin_settle (override): admin only, and only if unsettled and Clock >= close + delay (1 hour or more); it records the manual price and emits an event. pause / unpause: admin (a separate pause-guardian role that can only pause, not unpause, is the Compound pattern). redeem: anyone holding tokens, never pausable. Yes/No mint authority: a PDA owned by the program (seeded by market and side), so tokens can only be created through mint_pair; freeze authority set to none, so no key can freeze redeemers. No human or backend key ever holds mint authority.

**Against:** (1) Permissionless settle introduces a selection problem: if more than one valid oracle update exists inside the window, the caller can choose the favourable one, so the program must define a canonical choice; the spec text ('Settle Market ... called by the automation service') suggests a restricted caller, which is simpler to reason about, at the price of liveness depending on one key. (2) A separate operator role gives a hot key the power to create junk or mis-strike markets (spam, wrong strikes); with a single admin key you reduce roles but the hot key then has override, pause and config power, which is worse. (3) A freeze authority of none removes a compliance lever some issuers want; that is a legal-lens question for another group. (4) Mint authority per market PDA versus a single config PDA: per-market limits blast radius but costs more accounts. (5) If the CLOB is external (Phoenix or OpenBook), order permissions are governed by that program, not ours.

### D27 (decision)

Beyond the eight spec functions, the full lifecycle needs these. (1) merge_pair (burn one Yes plus one No for $1.00 USDC before or after settlement). The spec's Sell No path ends with 'holding both Yes + No = $1.00 worth of redeemable USDC', and Gnosis CTF ships mergePositions for exactly this. It conflicts with the spec invariant 'Tokens can only be destroyed via the redeem function', so the invariant should be reworded to 'only via redeem or merge'. (2) update_config / set_admin (two-step) for rotating a compromised key, changing the confidence threshold, staleness window, oracle feed or ticker list; the spec's Initialize Config is 'one-time'. (3) close_market / reclaim rent: after settlement and once outstanding pairs reach zero, close the order book market and rent-bearing accounts (Anchor close constraint; OpenBook has a close_market_admin; Phoenix has Closed then Tombstoned). Redeemability 'indefinitely' means the vault and mints cannot be closed while tokens exist. (4) Order-book plumbing, depending on the CLOB: cancel-all or force-cancel at close, and consume_events/crank if the CLOB needs one (OpenBook v2 has a consume_events_admin; Phoenix is crankless), plus seat or balance withdrawal. (5) withdraw_fees if any fee is charged (spec: fees must live in a separate account). (6) Optional: set_trading_halt per ticker, and a read-only view helper for the UI. The Pyth price update posting is done by the Pyth receiver program, not by us.

**Against:** Every extra instruction is attack surface and test burden, and the spec is explicit about a 'must exist' list. A minimal build could skip merge_pair: users hold Yes plus No until settlement and redeem the winner, which works for a 0DTE product but locks capital until 4 PM and makes the 'system handles the close automatically' sentence in Sell No false. Rent reclaim (close_market) can be left out of a devnet demo since devnet SOL is free. update_config could be replaced by redeploy on devnet. If the team chooses an existing CLOB, items in (4) shrink to nearly nothing.

### Q12 (open question)

Three candidate meanings of 'sub-second finality', with the evidence. (A) PROCESSED: about 0.4 s, can be rolled back (Solana docs: 'newest view, but it can still be rolled back'); Helius estimates about 5 percent of processed transactions drop (secondary). (B) CONFIRMED (optimistic confirmation, more than two-thirds of stake has voted): about 0.6 s per Helius (secondary); Helius also says no confirmed block has ever reverted (secondary, unverified here). This is what the industry normally means by 'sub-second' on Solana today, and Solana docs recommend confirmed for blockhash fetches. It is not finality in the strict sense. (C) FINALIZED (maximum lockout): about 12.8 s on mainnet today under TowerBFT per solana.com, about 13 s (10 to 20 s) per Helius. By that strict reading mainnet does NOT meet 'sub-second finality'. Upcoming change: Alpenglow targets about 150 ms true finality (solana.com calls it 'an expectation, not a constant'). As of 9 Oct 2026, solana.com still lists mainnet and devnet activation as expected, and a news report says mainnet has not activated, testnet has run it since 22 Sep, and the next mainnet feature-activation window is 9 Nov (secondary; sources disagree on dates). Slot time: reports say mainnet moved from 400 ms to 200 ms slots at epoch 1053 on 9 Oct 2026 (secondary, partly inconsistent). Devnet normally runs the same release branch as mainnet or a newer minor, so its times track mainnet but with more variance. Direct measurement was NOT done (see gaps). A way to measure: send a trivial transaction, record send time, then poll getSignatureStatuses and log when confirmationStatus becomes processed, confirmed, finalized, 50+ times on devnet and mainnet.

**Against:** What would change the picture: (1) a direct measurement on devnet showing confirmed latency well above 1 s, or finalized latency far from 13 s; (2) Anza confirming Alpenglow activation on devnet or mainnet (then finalized becomes about 150 ms and the strict reading is satisfied); (3) the spec author or grader stating which level they mean; (4) evidence of confirmed-level reversals on devnet (a less stable cluster that may be reset).

### Q25 (open question)

Who can upgrade: whoever holds the program's upgrade authority. By default it is the deploying CLI wallet, and the authority can deploy new code or close the program (Solana docs). Because the program owns the settlement accounts and its code enforces 'immutable once written', anyone who can upgrade the program can in principle change that rule, so the claim holds only as long as the upgrade key is trusted, or is removed. Options with evidence: (1) Single deployer key kept as authority: simplest, needed during development and devnet resets, but a single point of failure. (2) Transfer to a Squads multisig (Squads docs describe transferring program upgrade authority to the Squad vault, upgrading via a buffer, and a 'Safe Authority Transfer'); add a time lock (Squads time locks of 1 hour, 1 day, 1 week or custom delay all approved Squad transactions; the developer reference does not say whether program upgrades are covered, so test it). Squads v4 warns of config-authority compromise and over-long time locks. (3) Two-step transfer through Pyth's program-authority-escrow so a wrong destination key can be reverted. (4) Make immutable with solana program set-upgrade-authority --final: 'Once a program is immutable, it can never be updated or closed' (no bug fixes, rent cannot be reclaimed; and a verified-build PDA must exist before finalizing or OtterSec must be contacted). (5) Hybrid: upgradeable and multisig-held during pilot, finalize after audit and a stable period. Publish verified builds (solana-verify) so users can check the deployed code matches the repo, but note this proves source match, not safety. Phoenix publishes a verification path; its upgrade authority status was not found.

**Against:** What would change the picture: the actual threat model and timeline. If the project stays on devnet only, a single key is correct and 'immutable' is unattainable (devnet resets, redeploys). If mainnet is real, evidence that a time lock covers program upgrades in Squads, an audit result, or a bug found after launch would favour option 2 or 5 over finalizing; a regulator-facing or user-trust requirement for 'no admin can change rules' would favour option 4. Also unknown: whether users and graders accept 'immutable' as a statement about data (outcome never rewritten by program logic) rather than about code.

### Q26 (open question)

Options. (A) Next.js (spec recommended; official Solana template exists as kit/nextjs in solana-foundation/templates; React docs recommend starting with a framework; 'All the frameworks on this page support client-side rendering, single-page apps, and static-site generation' and can be deployed to a CDN without a server). With output: 'export', Next.js 16 (docs v16.4.0) emits plain HTML/CSS/JS to the out folder, deployable to any static host, including GitHub Pages (Next.js ships a template), Nginx, Cloudflare Pages or Vercel. Unsupported in a static export: Server Actions, cookies, rewrites, redirects, headers, ISR, default image optimization, request-reading route handlers. Wallet code must be client-only (window access guarded in useEffect). (B) Plain React with Vite: React docs treat building from scratch as the exception; Vite builds to dist and deploys to GitHub Pages, Cloudflare Pages, Netlify or Vercel; SPA fallback routing must be set per host; you choose your own router and data fetching. (C) Next.js with a server (Cloudflare recommends vinext on Workers for full-stack Next.js; not static). Evidence relevant to 'no server-side work': Pyth's Hermes now requires an API key, so any browser price feed from Hermes needs a proxy (the backend can supply it) or the key is public. Solana Foundation templates exist for Next.js; I did not find an official Vite template in the page opened.

**Against:** What would change the picture: (1) a requirement for server-rendered pages, share cards, or API routes (would favour Next.js with a server); (2) build or deploy friction with static export on the chosen host (Cloudflare points full-stack Next.js to a different adapter); (3) a grader expecting 'Next.js' literally; (4) evidence that wallet-adapter or Kit-based libraries behave better with Vite; (5) the Hermes proxy decision, which decides whether the site is truly static.

### Q44 (open question)

Options for what Pause stops, with how comparable protocols behave. (1) Literal spec: stop minting and trading only (create orders, fills); cancel, merge/redeem and settlement keep working. Phoenix's Paused status is this shape: 'Only reductions and withdrawals are accepted'; PostOnly allows placements, reductions and withdrawals; Closed lets the market authority force-cancel all orders. (2) Granular flags: Compound III has separate pause flags for supply, transfer, withdraw, absorb and buy collateral, settable by the Governor or the pause guardian; Drift has separate bits for DepositPaused, WithdrawPaused, FillPaused, LiqPaused, AmmPaused and others. (3) Aave V3 two tiers: freeze blocks only supply and borrow (withdraw, repay and liquidation still work); pause blocks supply, borrow, withdraw, repay and liquidation (every validate function checks isPaused). (4) Nothing pausable on the exit path: Gnosis ConditionalTokens (the design behind Polymarket's tokens) lists no pause check on mergePositions or redeemPositions in the code opened, and reportPayouts can only be done once per condition. (5) Irreversible shutdown: Maker's emergency shutdown module is triggered by MKR holders, is deprecated, and cannot be undone; redemption mechanics were not retrieved. Trade-off visible in the evidence: the more a pause key can stop (especially redeem or settle), the more users must trust that key with their funds; the fewer it stops, the less it helps in an incident such as a bad oracle write. Open design points: whether pause cancels or freezes resting orders, whether a pause that lasts past 4 PM still allows settlement and redeem, and whether unpause needs a different or slower key than pause.

**Against:** What would change the picture: (1) a concrete incident model: if the worry is an oracle or program bug that could mis-pay, a settlement-level pause is valuable; if the worry is theft via a compromised admin key, a pause that can never block redeem is safer; (2) audit feedback on the pause key's power; (3) evidence of how users and graders interpret 'pause minting and trading' (the spec lists only those two); (4) whether the chosen CLOB program has its own pause semantics that Meridian cannot override.

### Q53 (open question)

Options by layer. ON-CHAIN: Anchor events for create_strike_market, add_strike, mint_pair, merge, settle (with oracle price, confidence, publish_time and slot), admin_settle (manual price plus reason hash), pause/unpause, config and admin changes, redeem. emit!() writes base64 data to program logs, is simple, and can be subscribed to, but 'data providers may truncate program logs, so emit!() events can be lost'; emit_cpi!() puts events in self-CPI instruction data, costs extra compute, is less likely to be truncated, and cannot be subscribed to directly (fetch the transaction and decode inner instructions). Everything on-chain is public, so nothing secret or private may be put in an event. BACKEND: structured logs for each job run (start, per-market result, retries, end), a dead man's switch so a job that never ran raises an alert (Healthchecks.io: alert when an expected ping does not arrive, with start and fail signals and grace time), alert channels (email, Slack, PagerDuty, webhooks), wallet SOL and USDC balance, oracle confidence/staleness readings, slot lag via getHealth (error -32005 with numSlotsBehind), settlement latency against the 10-minute target. Never log keypairs, API keys, bearer tokens or connection strings; OWASP's exclude list also names access tokens, session IDs, encryption keys and sensitive personal data. Log authorization failures and use of break-glass accounts (the admin override). BROWSER: error and transaction-failure reporting with scrubbing of wallet-adjacent data; no secrets in the bundle. Third-party webhooks (Helius) can supplement on-chain monitoring but do not promise guaranteed delivery, may send duplicates, and are auto-disabled at 95 percent failure rate. Whether a wallet address counts as personal data is a legal question left to group 7 (Q49).

**Against:** What would change the picture: (1) for devnet-only core scope, much of this is optional; the spec lists monitoring only under the mainnet bonus; (2) evidence that the chosen RPC provider truncates logs (would force emit_cpi); (3) a legal conclusion that wallet addresses or IP addresses in browser telemetry are personal data (would push browser logging to near zero); (4) the cost and free-tier limits of Healthchecks, Sentry, or Helius, which I did not confirm; (5) a real incident showing which signal would have caught it.

Findings: F5.63, F5.64, F5.65, F5.66, F5.14, F5.04, F5.05

## Findings

### F5.01 [D17] [S20] CONFIRMED

The twelve-factor method stores config in environment variables because they live outside the codebase and are unlikely to be checked in; config files kept out of version control are weaker because it is easy to check one in by mistake.

- Lens: technical
- Source: [The Twelve-Factor App: Config](https://12factor.net/config): "The twelve-factor app stores config in environment variables."
- Verification (2026-10-09): held: Opened 12factor.net/config. Says config is stored in environment variables; little chance of being checked in accidentally; config files outside VCS easy to check in by mistake.

### F5.02 [D17] [S20] CONFIRMED

OWASP warns that environment variables are broadly exposed (all processes, logs, system dumps) and advises them only when other injection methods are not possible; prefers mounted secret files or a secret store; recommends rotation, least privilege and different secrets per environment.

- Lens: technical
- Source: [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html): "environment variables are generally accessible to all processes and may be included in logs or system dumps."
- Verification (2026-10-09): held: Opened OWASP Secrets Cheat Sheet. Env vars 'generally accessible to all processes and may be included in logs or system dumps'; 'not recommended unless other methods are not possible'; rotation, least privilege, per-environment secrets all present.

### F5.03 [D17] [S20] CONFIRMED

Anza's CLI documentation calls file-system keypairs the least secure way to hold SOL: the file holds an unencrypted keypair and a password only protects the seed phrase, not the file.

- Lens: venues
- Source: [Anza CLI: File System Wallet](https://docs.anza.xyz/cli/wallets/file-system): "File system wallets are the least secure method of storing SOL tokens."
- Verification (2026-10-09): held: Opened Anza file-system wallet page. 'least secure method of storing SOL tokens'; file holds unencrypted keypair; password applies to seed phrase, not file.
