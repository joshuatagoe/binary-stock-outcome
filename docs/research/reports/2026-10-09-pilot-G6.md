# Decision review 2026-10-09-pilot, group 6: Proof for the grader

Verified research for D4, D11, D18, D30, A2, Q23, Q24, Q55. Stories: S23, S24. Input: `docs/research/inputs/G6-proof-for-the-grader.md`.

## Items

### D4 (decision)

Follow the spec's preferred stack: Rust/Anchor 1.0 on Solana for the program, TypeScript/React/Next.js for the frontend, TypeScript/Node for the automation service. These are spec-stated preferences, so alternatives cost justification effort and gain little. Anchor 1.0 (April 2026) makes Surfpool the default `anchor test` backend (needs Solana 3.x, Surfpool >=1.1.2). If HyperLiquid is not built on, the spec only says to 'research and document feasibility if you explore this path'. So the docs need a short feasibility note: HIP-4 outcome markets exist on mainnet (since ~2 May 2026) but are curated (permissionless deployment is announced, not confirmed live), settle in USDH not USDC, and reference HyperCore mark prices (BTC first). That does not fit custom MAG7 daily-close markets with own program invariants. Alternatives: Solidity on an L2 (spec-acceptable; costs sub-second order-book latency justification), Pinocchio/native Rust (more code, less safety), Next.js alternatives like Vite (spec only 'recommends' Next.js).

**Against:** Anchor adds a third-party abstraction, and the spec says to 'avoid unnecessary third-party abstractions; justify all major dependencies'. Native or Pinocchio-style programs are smaller and cheaper in compute, and Anchor 1.0 / Surfpool is brand new (April 2026), so tooling churn risk is real. Also Windows needs WSL for the Solana toolchain, which hurts S23. HyperLiquid HIP-4 is closer to the product than the spec assumed (binary daily outcome markets exist natively), so dismissing it as 'no custom instruments' would be out of date; the docs must say why it still fails (curated deploy, USDH, no own-program invariants, no stock feeds confirmed).

### D11 (decision)

Provide a simulation/replay mode in addition to the real-oracle path: a clearly labelled 'demo mode' that uses a controllable clock and a mock or recorded price (a mock oracle account in the same Pyth PriceUpdateV2 format on localnet/devnet) so the full create-mint-trade-settle-redeem lifecycle runs at any hour. Keep the real-oracle path as the default for the scheduled daily jobs, and keep the settle instruction's staleness and confidence checks identical in both modes. Real Pyth US equity feeds only publish in the sessions Pyth documents (regular, pre, post, and Sun-Thu overnight; closed Fri-Sat), so a purely real-price design cannot be shown at arbitrary hours, and the spec's Operability metric says the demo must be reproducible.

**Against:** A simulation mode can look like faking settlement: the spec requires settle to 'read the stock's closing price on-chain from the oracle', and a mock oracle plus a time-bypass flag in the program is attack surface and a correctness risk (time checks 'only after 4:00 PM ET' must still be enforced on-chain). A grader may judge a mock as not demonstrating the real oracle path. Cheaper alternative: record one real settlement on devnet during market hours with tx signatures, and rely on tests with warped clocks for the rest.

### D18 (decision)

Solana remains the leading host. Candidates: Solana (spec-recommended; slot ~400 ms, existing on-chain CLOBs such as Phoenix and others, Pyth receiver on devnet); EVM L2s such as Arbitrum or Base (acceptable if order-book latency is justified; Base/Arbitrum sequencer pre-confirmations are fast but L1 finality is slow); HyperLiquid (HyperCore HIP-4 binary markets exist, but the market logic is the chain's, not the project's own program, which breaks the requirement that functions and invariants live in the project's program); other chains (Sui with DeepBook, Aptos, Sei, Monad, etc.) were not verified in this review. Docs must say: why Solana, what finality means (confirmed vs finalized), the alternatives and why not, and that any CLOB used is called via CPI while mint, settle and redeem and the vault invariant live in the project's own program.

**Against:** 'Sub-second finality' is not literally true on Solana: optimistic confirmation takes about 0.4 to 1 s but full finalization takes about 12.8 s (not verified in this run), so the docs must define the term honestly. Solana's devnet has had outages, and a chain with a sturdier testnet would serve the grader better. Relying on an external CLOB (Phoenix) introduces a dependency whose devnet deployment could not be confirmed in this review, whereas building the book in-program meets the 'functions in your program' reading most cleanly but costs most effort.

### D30 (decision)

Test plan layers: (1) unit tests per instruction with LiteSVM (in-process, fast) or Mollusk for single-instruction checks; (2) property or fuzz tests for the invariants (Yes+No=$1 over a sweep of prices including at-strike, vault = $1 x pairs after every mint/redeem, with Trident or proptest); (3) integration lifecycle on Surfpool/solana-test-validator through `anchor test` (Anchor 1.0 default is Surfpool; `--validator legacy` keeps solana-test-validator); (4) oracle tests with fabricated PriceUpdateV2 accounts for stale, wide-confidence, wrong-feed and valid cases; (5) a devnet smoke script. Gaps in the spec's list for a product with an order book, oracle and scheduled jobs: account-validation/authorization negative tests (wrong mint, wrong vault, non-admin), pause behaviour, double-settle/immutability, admin-override delay boundary, rounding and dedup of strikes, DST and holiday and half-day calendars, automation-job tests (retry/backoff, idempotency on restart, missed run, clock timezone), CLOB CPI integration (partial fills, self-trade, cancel after settle), settlement-after-close order cleanup, compute-unit budgets, and crash-recovery of the automation service.

**Against:** This is a large surface for a time-boxed project. Fuzzing and CLOB-edge tests may cost more than they buy next to the 4 spec-listed items, and the tool landscape (Surfpool, LiteSVM, bankrun deprecation) is moving fast and mostly confirmed only through third-party write-ups. A smaller plan (LiteSVM unit + a few invariant sweeps + one full lifecycle) hits all spec bullets and may be the right scope.

Findings: F6.12, F6.13, F6.14

### A2 (decision)

Devnet is explicitly unreliable: Solana docs say it 'may be subject to ledger resets', there is no SLA, and the Feb 2024 mainnet-halt bug was first found during a devnet outage. Mainnet had seven full halts 2020-2024 per Helius; a complete devnet halt/reset record was not found. To keep a verifiable record of a day lost to an outage, the project can: log every automation run (job id, intended time, RPC endpoint, result, tx signature or error) to an append-only log committed or hash-anchored off chain; save RPC health evidence (getHealth, getSlot, the status page snapshot) at failure time; archive the strike/price inputs; keep scripts that can re-run a day from recorded inputs; and publish the program ID, deploy tx and a program-version hash so a reset can be redeployed and shown consistent. After a reset, redeploy from scripts and note the reset in a dated incident log in the docs.

**Against:** Off-chain logs are self-reported and not independently verifiable, and a ledger reset destroys the on-chain evidence, so graders may not trust it. A stronger alternative is to also run a local validator or mainnet-fork day and record it, or to deploy to a second cluster; the cost is more infrastructure. I also could not find an authoritative devnet reliability record, so any quantitative claim in the docs would be unsupported.

Findings: F6.15, F6.16, F6.17

### Q23 (open question)

Options for how a devnet-halt day counts against the 'every trading day' liveness metric: (a) count it as a miss and show the cause (honest, hurts the score); (b) exclude it as an infrastructure force majeure with an evidence bundle (RPC health logs, cluster status, failed-tx logs) and a late-settled catch-up; (c) settle late via admin override or a catch-up run when the cluster recovers, and report time-to-settle separately from the 10-minute target; (d) show liveness on a second environment (local validator or simulated clock) for the days devnet failed. Evidence: Solana docs say devnet is not a stability-guaranteed cluster; the spec itself defines the failure path (retry 15 minutes, then admin override after a 1 hour delay) but only for oracle failure, not chain failure; the spec's Bonus mainnet note ties production-grade liveness to mainnet. Graders can be asked by stating the interpretation up front in the README/risks note, naming the rule (e.g. 'a trading day counts if devnet was healthy per the evidence bundle'), and flagging it to the course staff or in the submission form before the deadline; no source says who the graders are or what rubric they use.

**Against:** Evidence that would change the picture: an explicit grader rubric or instructor answer saying devnet outages are excluded (or not), a documented devnet outage on a specific trading day, or the devnet reliability record over the project window. If graders only check the lifecycle once, the metric is moot.

Findings: F6.15, F6.16, F6.18

### Q24 (open question)

Options for a grader running in the evening or at a weekend: (1) rely on Pyth's extended sessions: Pyth documents pre-market 4-9:30, post-market 4-8 PM, overnight Sun-Thu 8 PM-4 AM ET, so weekday evenings may still have a live price, but Friday night and Saturday are closed, and the price is not a 4 PM close; (2) demo/simulation mode with a mock oracle account and an adjustable clock (D11); (3) a replay of a recorded real settlement, plus pre-recorded tx signatures and a video; (4) a keeper-fed manual price through the admin-settle path after the delay (shows a different instruction, not the oracle read); (5) local validator with a Surfpool or cloned mainnet account state. Each trades realism against reproducibility; a mock path must not weaken on-chain time and staleness checks.

**Against:** What would change this: confirming that Pyth publishes devnet equity feeds that update outside regular hours (not found), that a Hermes API key is free and easy to get, and how graders actually run the project. If the real feed updates weekdays 4 AM-8 PM only, the evening gap shrinks to weekends and Friday night.

Findings: F6.05, F6.06, F6.07, F6.19

### Q55 (open question)

A one-command setup on all three OSes is feasible only with caveats. Windows: the official Anchor and Solana docs say Windows development must go through WSL, so the realistic Windows path is 'run make dev inside WSL' (or a Docker/devcontainer), not native PowerShell. macOS/Linux: a script can install Rust, the Solana/Agave CLI 3.x, Anchor 1.0 (via AVM), Surfpool >=1.1.2 and Node, then run a local chain. Needs: a local chain (Surfpool/solana-test-validator, no key, no SOL limit) for the no-network path; for devnet: devnet SOL via the faucet (rate-limited, airdrops often fail), a funded keypair, and an oracle access key, since Pyth's Hermes now 'requires an API Key' after the Core upgrade completed on 26 Aug 2026. Possible blockers: toolchain version drift (Solana 3.1.10 recommended), long first build/compile, faucet limits, public devnet RPC limits (100 requests/10 s per IP), missing API key, Windows without WSL, and OneDrive-synced paths (this repo lives in OneDrive).

**Against:** What would change the picture: native Windows binaries for the Agave 3.x CLI (not found), a Dockerised dev image that the grader accepts, or a free no-key Hermes tier or a replay fixture that removes the key need. A two-tier command (`make demo` local with mock oracle, no keys; `make devnet` with keys) would remove most blockers.

Findings: F6.20, F6.21, F6.22, F6.23
